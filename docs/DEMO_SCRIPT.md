# WareTrack — Demo Script

A ~5 minute click-by-click walkthrough designed for the course presentation. Total demo budget: keep code-talk short, let the running app do the talking.

## Pre-demo checklist (5 min before)

- [ ] MySQL is running, `waretrack_db` is loaded
- [ ] Backend running: `cd backend && npm run dev` (check `http://localhost:4000/health`)
- [ ] Frontend running: `cd frontend && npm run dev`
- [ ] Browser tab open at `http://localhost:5173`
- [ ] Have GitHub repo URL ready to share
- [ ] (Optional) MySQL Workbench open in the background for raw-SQL questions

## 1. Open — 30 sec

> "WareTrack is a full-stack inventory and logistics platform I built for the DBS project. It models a real B2B warehousing operation — companies like BigBasket and Apollo storing goods in our warehouses across India, with monthly invoicing, expiry tracking, and capacity planning. The course required 13 tables and basic SQL features — I extended it to 19 tables with 6 stored procedures, 8 triggers, and 12 advanced analytical queries."

Land on the **Dashboard**. Let them see it for 3-5 seconds — the visual establishes credibility before you say a word.

## 2. Dashboard — 45 sec

Point out:
- **5 warehouses, 12 active clients, 31 SKUs, ~₹37 lakh inventory value** — all live numbers from the database
- **Critical alerts: 2/5** — these come from triggers detecting expiring stock and low inventory
- **Monthly revenue chart** — outbound shipment value over time, calculated by joining `OutboundShipment` and `ShipmentItem`
- **Warehouse utilization bars** — driven by a stored function `fn_get_available_capacity`
- **Top clients** — aggregated revenue per client across all dispatches

> "Every number on this page is a live SQL query — nothing's hardcoded. Most are aggregates with JOINs across 3–4 tables."

## 3. Inventory — 30 sec

Click **Inventory** → filter by **Expiring 30d**.

> "These three SKUs are flagged as expiring soon — Mother Dairy milk batches with 3–5 days left. The amber color and the days-left counter come from a stored function `fn_days_until_expiry` that I call directly from the API. The expiry alerts in the Alerts tab were auto-generated by a stored procedure `sp_generate_expiry_alerts` that scans the SKU table and inserts into StockAlert."

Switch filter to **Low Stock** — show the Volini spray and HP laptop with critical alerts.

## 4. Shipments — 60 sec (the live trigger demo)

Click **Shipments** → **New Outbound**.

Fill in:
- Warehouse: **WH-MUM-01 Mumbai**
- Client: **Reliance Retail**
- Address: **BKC Mumbai**, City: **Mumbai**
- Item 1: **SKU-RR-001-B1 Good Life Sugar**, qty **50**, unit price **45**

Click **Create Shipment**. The shipment appears at the top of the list as **DISPATCHED**.

> "When I clicked create, the backend called a stored procedure `sp_process_outbound_shipment`. That procedure ran inside a transaction — it inserted the shipment header, then inserted the line items. Inserting each line item triggered TWO things automatically: first a `BEFORE INSERT` trigger that checks if there's enough stock and the SKU isn't expired — if not, it raises a SIGNAL and the whole transaction rolls back. Then an `AFTER INSERT` trigger decrements `StockLedger.quantity_on_hand` for that warehouse. **The application code didn't touch StockLedger at all** — the database enforces inventory integrity itself."

(Optional, if you have a minute) Try to create another outbound with quantity 99999 — show the error response from the SIGNAL.

## 5. Invoices — 45 sec (trigger #2)

Click **Invoices** → pick any **PARTIAL** invoice → **Record Payment**.

Enter the balance amount → submit.

> "When I record this payment, the trigger `trg_payment_update_invoice` fires — it adds to `amount_paid` and updates `status` to PAID if the balance is cleared, or PARTIAL if it's not. It also generated an audit log entry via `trg_audit_invoice_changes` — every change to sensitive tables is captured in JSON in the `AuditLog` table."

Show the updated row turns green / status flips to **PAID**.

## 6. Reports — 90 sec (the viva-bait page)

Click **Reports**.

> "This is where I went well above the rubric. The course asked for nested and correlated subqueries — I built 12 reports, each demonstrating a different advanced SQL technique."

Click through 3-4 examples — pick the most visually impressive ones:

- **Top 3 Clients per Warehouse** — "This uses `RANK() OVER (PARTITION BY warehouse_id ORDER BY revenue DESC)` — a window function, more efficient than a correlated subquery for top-N-per-group."
- **Month-over-Month Growth** — "This is a CTE feeding into `LAG()` window function to compute the previous month's value in the same row — that lets us calculate growth percentage in pure SQL without app-level math."
- **Client Health Snapshot** — "Two CTEs joined together: one aggregates inventory per client, the other aggregates financials. The final `CASE` derives a health rating — EXCELLENT, GOOD, WATCH, AT_RISK."
- **Clients with Zero Alerts** — "Correlated `NOT EXISTS` — find clients where no row exists in `StockAlert` that traces back to their products."

> "The descriptions on the left tell the viva examiner exactly which SQL concept each query demonstrates. Every one of these has been validated against MariaDB."

## Anticipated viva questions & answers

**Q: Show me a complex SQL query and explain it.**
→ Open Reports → MoM Growth. Walk through: the CTE computes per-warehouse monthly totals, then `LAG()` partitioned by warehouse and ordered by year/month pulls the previous row's value into the current row, then the outer SELECT computes `(current - prev) / prev * 100`.

**Q: How do you ensure data consistency?**
→ Three layers. (1) CHECK constraints and FK constraints at the schema level. (2) Triggers that enforce invariants (no negative stock, no expired dispatch, payment auto-reconciliation). (3) Stored procedures wrap multi-step operations in `START TRANSACTION` with `EXIT HANDLER FOR SQLEXCEPTION` that rolls back on any failure.

**Q: Why stored procedures instead of putting that logic in the backend?**
→ Atomicity and locking. `sp_transfer_stock_between_warehouses` uses `SELECT … FOR UPDATE` to lock the source row while it decrements one warehouse and increments another. Two concurrent transfers can't oversubscribe stock. Doing that round-trip from Node would require an explicit transaction and multiple network hops; doing it in the DB is one call, one transaction.

**Q: What normal form is your schema in? How did you verify it?**
→ 3NF, with BCNF holding as well. Verification: walked through every table, listed functional dependencies, confirmed every non-key attribute depends directly on the PK with no transitive chains. The detailed walkthrough is in `docs/NORMALIZATION.md`.

**Q: Show me a trigger and walk through what it does.**
→ Open `03_triggers.sql` → show `trg_outbound_item_check_stock`. Explain: BEFORE INSERT on ShipmentItem for OUTBOUND type, looks up current stock in StockLedger, raises SQLSTATE 45000 if insufficient. Combined with the AFTER INSERT trigger that decrements stock, dispatching never produces a negative balance.

**Q: How would this scale?**
→ The schema indexes the hot columns (warehouse_id, dispatch_date, status). Beyond a million rows we'd partition `ShipmentItem` and `AuditLog` by month and add covering indexes for the dashboard queries. The frontend is already paginated-ready — the Reports page caps at 50 rows for that reason.

**Q: What did you find most challenging?**
→ The trigger ordering. MySQL fires BEFORE INSERT triggers in undefined order if you have multiple — I had to consolidate the capacity check and the stock check into separate triggers that don't conflict, and make sure the AFTER trigger only fires after BEFORE validation passes. Took some iteration to get right.
